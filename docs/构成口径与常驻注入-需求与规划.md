## 一、问题一：面板说 3k，实际首轮 16k

### 1.1 现象

项目 `temp`（cwd `/Users/openclaw/dhs/temp`）在面板里「合计少发 ≈36.1k」，概览折算下来约 3k；
但 `session-34a72ee8-289e-4831-97ee-826dcdeaeae4` 第一轮第一步的真实请求是 **16.3k**。

会话「上下文浏览器」明细：系统提示词 ≈1.9k（12%）+ 工具定义 ≈10.8k（69%，**45 项**）+ 注入 2.1k（13%），合计 15.8k。

### 1.2 根因（已定位到行）

插件统计的工具表来自 `getService(ctx,"tools").schemas()` —— **不带 scope、不带 toolSet**，拿到的是「全局平面」的 174 个工具（≈43.4k token）。
而这个会话跑在 `standard` 预设上，预设会把工具收窄到 agent scope；真实请求里只有 45 个工具（≈11.1k）。

两边差 129 个工具，且**不重合**：

- 插件认为「会发」的 174 个里，只有 13 个真的发出去；
- 真实发出去的 45 个里，有 32 个（`bash` / `edit` / `write` / `skill` / `subagent` / `web_search` / `plugin_manager` …）**根本不在插件的工具表里**。

后果有两层：

1. **少发被夸大**：`mcp:github` 46 个工具、`plugin:agent-teams` 23 个工具本来就不在请求里（预设已把它们排除），面板却把它们算成「隐藏省下的 ≈36.4k」。
2. **实际发送被低估**：`projected.total` 只有 **5,221**，因为 32 个真实存在的工具没被计入；真实请求是 16.3k。

相关代码：

- `lib/index.js:249 catalogTools(runtime)` —— `schemas()` 无 scope；
- `lib/index.js:274 attachTools(runtime, prompt)` —— 装配结果没工具时用这份全局表补齐；
- `lib/index.js:1679` 的 `system-prompt/assemble` 监听 —— 只 `describeAssembly(assembled)`，没用 `context.toolSet`；
- 宿主侧 `dsh-agent-loop/lib/index.js:687` 先 `tools.resolve({agent,...})`，再把 `toolSet` 传进 `assemble`（`:696`）；
- `dsh-tools/lib/index.js:590 schemas(scope, toolSet)` 支持按步工具集取值。

### 1.2.1 先行验证结果（已实测，2026-11-15）

按「第五点风险先行测试」的要求，先把三条风险全部跑了一遍，结论如下。

**① `context.toolSet` 能不能拿到 —— 能。**

在 `system-prompt/assemble` 里临时加了诊断字段并重载实测：

| 字段 | 值 |
| --- | --- |
| `hasToolSet` | `true` |
| `toolSetHasView` | `"function"` |
| `tools.schemas(agent, toolSet)` | **46** |
| `tools.schemas()`（全局） | 174 |

46 与真实请求的 45 差 1，是条件注册（`when`）在两步之间切换导致的正常抖动，不是口径错误。
**结论：F1-1 主修可行，不需要赌。**

**② token 估算差多少 —— 差在公式，不在精度。**

宿主自己有一套固定密度估价（`@deepseek-ai/dsh-token-meter/lib/types/estimate.js`）：

```js
const CHARS_PER_TOKEN = 4;
const BLOCK_OVERHEAD = 4;
// 工具：Math.ceil(JSON.stringify(header.tools).length / 4) + 4
```

拿同一份 45 个工具实测：

| 公式 | 结果 | 与浏览器显示（×45 ≈10.8k）差 |
| --- | --- | --- |
| 宿主 `ceil(json/4)+4` | 10,793 | **−0.1%** |
| 逐项 `ceil(json/4)` 求和（不加 overhead） | 10,796 | +0.03% |
| 插件现行 `cjk + other/3.6` | 12,065 | **+11.7%** |

段落/运行时注入同理（13 段合计）：宿主 2,132、逐项无 overhead 2,138（+0.28%）、插件现行 2,629（**+23.3%**）。

**结论：把 `lib/tokens.js` 的密度改成 `4 字符/token`、逐项不加 overhead，就能与宿主数字对齐（误差 <0.3%），
不需要引入分词器；差的那 11%–23% 全是公式造成的。**

**③ 常驻注入的 token 会不会被低估 —— 会，而且是 CJK 最严重。**

| 文本 | 字符 | 宿主 | 现行 | 比值 |
| --- | --- | --- | --- | --- |
| `只保留结论与文件路径，不要日志全文` | 17 | 9 | 17 | 1.89× |
| `回答用中文，先给结论再给证据；…` | 29 | 12 | 29 | 2.42× |
| 300 个 ASCII 字符 | 300 | 79 | 83 | 1.05× |

现行公式给中文按 1 字 1 token 算，宿主按 4 字符 1 token 算。**必须统一到宿主公式**，
否则常驻注入一上线，面板立刻显示「注入 ≈35 token」而宿主显示 ≈14，又是新的自相矛盾。

> 注：宿主的 4 字符/token 对中文是**低估**（真实分词器约 1–1.5 token/汉字），
> 但面板要跟用户看到的宿主数字一致，所以统一用它，并在 UI 上继续标 `≈`。

### 1.3 修复方案

**F1-1｜按步工具集取真实工具表（主修）**

在 `system-prompt/assemble` 里优先用本步的 `context.toolSet`：

```js
const toolsService = getService(runtime.ctx, "tools");
const live = toolsService.schemas(context.agent, context.toolSet); // 45 个
```

- 拿到后写一份「本会话真实工具集」`runtime.liveToolsByAgent.set(agentId, {names, at})`，并作为该会话的 snapshot 工具清单；
- `attachTools()` 优先用会话级真实工具集，只有在拿不到时才退回全局 `schemas()`；
- `runtime.toolCatalog`（只增不减的界面目录）保留不变——它仍然用来「把关闭的东西打开」。

**F1-2｜区分「全局目录」与「本轮实际」两个口径**

- 能力条目（技能/MCP/插件）的 `tokens` 保留全局目录口径（用于比较大小、决定隐藏哪一项）；
- 新增 `entries[].liveTools` / `liveTokens`：本会话真实会发的部分；
- 面板统计新增「本轮实际发送」，与「合计少发」并列（见问题二）；
- 当某项能力的工具 0 个在本轮工具集里，标注「本轮不含」而不是「省下 N token」。

**F1-3｜少发只统计「真的本来会发」的部分**

`saved` 改为：`Σ(该项在本轮工具集里的工具 token + 该项说明段 token)`，并且只在它确实是「因为档位才没发」时计入。
因预设收窄而不存在的工具，不算少发。

**F1-4｜token 公式统一到宿主口径**

`lib/tokens.js:26` 现在是 `Math.round(cjk + other / 3.6)`，与宿主 `@deepseek-ai/dsh-token-meter`
的 `Math.ceil(chars / 4)` 不一致（实测工具 +11.7%、段落 +23.3%、中文短句 +89%）。
改为与宿主同形：

```js
export function estimateTokens(text) {
  if (!text) return 0;
  return Math.ceil(String(text).length / 4);
}
```

`lib/prompt.js:39 toolTokens()` 同步改为 `Math.ceil(JSON.stringify(tool).length / 4)`；
`client.js:225 estimateLocal()` 同步。这是全站唯一口径源头，改完 §三·五 的 D 组即可一次对齐。

### 1.4 验收标准

| # | 场景 | 期望 |
| --- | --- | --- |
| A1 | `temp` 项目、`standard` 预设会话 | 面板「本轮实际」≈ 上下文浏览器第一步读数（误差 <2%，按宿主公式对齐后应当几乎一致） |

## 二、问题二：档位统计行缺「当前合计发送」

> 这一条**不包含**问题一漏掉的东西，两者是互补的：问题一修的是「数字取错了工具表」，
> 本条修的是「只有省、没有发」。只做本条不做问题一，会得到一个精确显示的错误数字；
> 只做问题一不做本条，用户仍然判断不了这行与真实请求的关系。

### 2.1 现象

`加载 0 ≈0 · 只留简介 0 ≈0 · 默认不加载 31 少发 ≈36.4k · 合计少发 ≈36.1k`

只有「省了多少」，没有「现在到底发多少」。用户无法一眼判断这行数字与真实请求的关系。

### 2.2 方案

同一行补两项，顺序为「发 → 省」：

```
● 加载 1 ≈340   ● 只留简介 0    ● 默认不加载 31 少发 ≈36.4k
                                   合计发送 ≈340 · 合计少发 ≈36.4k
```

- 「合计发送」= 所有 `on` 档位条目的 `liveTokens`（本轮真实口径）；
- 两者分子相同、口径一致，避免 3k/16k 那种自相矛盾；
- 悬停/ⓘ 说明：这一行只统计技能/MCP/插件；系统提示与工具的整体数字在「构成」页头。

### 2.3 验收

- 该行任意时刻都同时给出「合计发送」与「合计少发」；
- 两者之和 ≈ 该页「全量」数字（同口径下闭合）。

## 三、新功能：额外要求常驻注入

> **与问题一的关系**：不包含。问题一是「统计口径拿错工具表」，问题二是「统计行缺一半数字」，
> 问题三是「新增一段每次请求都要发的文本」。三者共享同一个分母——一旦常驻注入上线，
> 它就必须走进「本轮实际发送」，否则会立刻重演 3k/16k 那种自相矛盾。
> 所以实施顺序上，问题一/二必须先落地，问题三才有可信的计量基础。

### 3.1 需求

胶囊浮层「概览」页的「额外要求（可选）」目前只用于一次性压缩指令（`lib/session.js:182 buildCompressionPrompt`）。
用户希望：**把它变成可常驻的指令**——打开开关后，每次请求都自动注入，不必重复输入。

同时，「概览」里所选的项目要能被记住/作为默认作用域。

### 3.2 设计

**数据模型（`modes.json`，version 4 内向后兼容）**

```jsonc
{
  "notes": {
    "global":       { "text": "", "enabled": false },
    "projects":     { "<projectId>": { "text": "只保留结论与文件路径", "enabled": true } },
    "sessions":     { "<sessionId>": { "text": "", "enabled": false } }
  },
  "ui": { "lastProjectId": "ws:c498e8d7-…" }   // 胶囊/面板上次选中的项目
}
```

- 三层与能力档位同构：会话 > 项目 > 全局，各自独立；
- `enabled=false` 时只保存文本、不注入；`text` 上限 2000 字符；
- `ui.lastProjectId` 只影响界面默认选中，不影响规则。

**注入实现**

在 `system-prompt/assemble` 里，按 `caps.project.id` + `agent.id` 解析出生效的那一条，非空且 `enabled` 时追加：

```js
sections.push({ name: "context-control:note", text: `## 常驻要求\n${text}` })
```

- 追加位置与 `context-control:brief` 同级（`withBrief` 的做法，`lib/index.js:625`）；
- 在「构成 → 系统提示」里作为一行出现，可单独关掉（关掉即写 `enabled:false`）；
- token 计入概览与「本轮实际」，不再被当成零成本。

**UI**

- 概览页「额外要求（可选）」右侧加开关：`每次发送都注入`；
- 打开后输入框变为常驻内容，下方提示「已随每次请求发送 ≈N token」；
- 「概览」的项目选择记住选中值，下次打开沿用（`ui.lastProjectId`）；
- 未输入内容时开关禁用，避免注入空段。

**API**

| action | 入参 | 说明 |
| --- | --- | --- |
| `setNote` | `scope`(global/project/session) `text` `enabled` `projectId` `sessionId` | 写入对应层 |
| `setUi` | `lastProjectId` | 记住选择 |

### 3.3 验收

| # | 场景 | 期望 |
| --- | --- | --- |
| N1 | 项目层开启并填文本，发消息 | 请求系统提示里出现「常驻要求」段，内容一致 |
| N2 | 关闭开关 | 不再注入，文本保留 |
| N3 | 会话层覆盖项目层 | 用会话文本；清空会话层回落到项目 |
| N4 | 同一项目下两个会话 | 互不影响（除非各自覆盖） |
| N5 | 空文本 | 不注入，开关置灰 |
| N6 | 「构成」里关掉该段 | 与开关联动，不出现两份 |

## 五、风险（均已先行实测，结论见 §1.2.1）

| 风险 | 实测结论 | 处理 |
| --- | --- | --- |
| 预设作用域拿不到 `context.toolSet` | 能拿到：`hasToolSet true`、`toolSetHasView "function"`、`schemas(agent,toolSet)=46` vs 全局 174 | 正常路径直接按步取；`__ccProbe` 等探测装配仍无 toolSet，退回全局并标「全局口径」 |
| token 估算与宿主差多少 | 差在公式不在精度：宿主 `ceil(json/4)+4` 与浏览器差 **−0.1%**；现行 `cjk+other/3.6` 差 **+11.7%**（工具）/**+23.3%**（段落） | 统一改 `CHARS_PER_TOKEN=4`（§三·五 D1–D3），验收收紧到 ±2% |
| 常驻注入被低估 | CJK 最严重：17 字短句宿主 9、现行 17（1.89×）；29 字宿主 12、现行 29（2.42×） | 必须先统一公式再上线；UI 继续标 `≈` |
| 条件注册（`when`）导致工具数抖动 | 46 vs 请求头 45，差 1 | 验收允许 ±2 个工具的抖动，不按固定数字断言 |
| 常驻注入放大上下文 | 每次请求重发，长文本一直占窗口 | 默认关闭；开启后 UI 显示「已随每次请求发送 ≈N token」，上限 2000 字 |

> 补充：宿主的 4 字符/token 对中文其实是**低估**（真实分词器约 1–1.5 token/汉字）。
